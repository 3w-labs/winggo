# Optimization 모드 비교 측정 (speed / balanced / quality)

동일 질의 **"강릉 맛집 추천해줘"** 를 세 모드로 실제 호출해 **한국 소스 비율 · 응답 속도 · 응답 품질**을 측정한 결과.

## 측정 조건

| 항목 | 값 |
|---|---|
| 측정일 | 2026-07-01 |
| 인스턴스 | `https://search.vsvs.kr/` (엔드포인트 `POST /api/search`) |
| 질의 | `강릉 맛집 추천해줘` |
| Chat 모델 | Grok (xAI) `grok-4.3` (전 모드 동일) |
| 임베딩 모델 | Transformers `Xenova/all-MiniLM-L6-v2` (전 모드 동일) |
| 검색 소스 | `web` + `social` + `academic` |
| 반복 | speed × 3회, balanced × 1회, quality × 1회 |

> 모델·임베딩·소스·질의를 전 모드 동일하게 고정했으므로, 차이는 **모드 자체**에서 기인합니다.

## 메트릭별 분석

### 1) 한국 소스 %

| 모드 | 한국 소스 % | 소스 수집 방식 | 해석 |
|---|---:|---|---|
| speed | 100% (성공 시) | 임베딩 유사도 필터 → 상위 결과 | 성공한 회차는 전부 한국 소스였으나 **표본이 10개로 얕음** |
| balanced | 75% | 임베딩 필터로 다회 검색, **36개 광범위 수집** | 영어 소스(리스트/여행 가이드)까지 폭넓게 섞임 |
| quality | 100% | LLM이 소수 고품질 소스 선별 → 본문 스크래핑 | **7개로 좁지만 전부 한국 소스**, 정밀 선별 |

- **balanced가 한국 소스 %는 가장 낮지만(75%) 절대 개수는 가장 많음(27개).** 넓게 긁어오면서 영어권 소스가 섞인 결과.
- speed·quality는 한국 소스 100%지만, 이유가 반대: speed는 **표본이 얕아서**, quality는 **LLM이 정밀 선별해서**.

### 2) 응답 속도

| 모드 | 속도(s) | 비고 |
|---|---:|---|
| speed | 16~49 | 실패 시 ~16s(조기 종료), 성공 시 ~49s. **속도 이점이 뚜렷하지 않음** |
| balanced | 51.9 | speed 성공 회차와 사실상 동일 |
| quality | 119.8 | 약 2~7배. **비스트리밍 호출은 Cloudflare 524(엣지 타임아웃)로 실패** → 스트리밍으로만 측정 가능 |

- **speed가 "빠르다"는 명제가 데이터로 성립하지 않음.** 실패해서 빨리 끝난 회차(16s)를 빼면, 성공한 speed(49s)는 balanced(52s)와 거의 같음.
- **quality는 공개 URL에서 비스트리밍으로 사용 불가**: 100초를 넘겨 Cloudflare가 524로 끊음(스트리밍 필요).

### 3) 응답 품질

객관 프록시(길이·구조·소스·언어) 기준:

| 모드 | 품질 등급 | 근거 |
|---|:--:|---|
| speed | **F (서비스 불가)** | 3회 중 **2회 답변 실패**(0소스, 폴백). 성공 1회도 311단어로 얕음 |
| balanced | **B** | 334단어, 소제목 구조, 36소스 근거. 안정적으로 답변 생성 |
| quality | **A** | 1,736단어 리서치 리포트, 소제목 8개, 정밀 선별 소스. 단 속도/타임아웃 리스크 |

## 핵심 발견

1. **speed는 신뢰성이 치명적으로 낮음 — 성공률 1/3 (33%).**
   3회 측정 중 2회가 소스 0건으로 답변 실패("could not find any relevant information"). 이는 앞서 이슈([#7](https://github.com/3w-labs/winggo/issues/7))로 등록한 "복원력 부재" 문제를 **실측으로 재현**한 것. speed는 재검색·재계획 루프가 없어 첫 검색 운에 결과가 전적으로 종속됨.

2. **speed의 "속도 우위"는 실측상 존재하지 않음.**
   성공 시 49s로 balanced(52s)와 동급. 빨랐던 회차(16s)는 **실패해서** 빨랐던 것.

3. **quality는 공개 엔드포인트에서 비스트리밍으로 사용 불가.**
   119.8s 소요 → Cloudflare 100초 제한을 넘겨 `524`. 스트리밍 호출로만 완주(2,672 청크, `done` 정상 수신). 운영상 프록시 타임아웃 정책 점검 필요.

4. **세 모드 모두 /api/search에서 한국어 질의에 영어로 답변.**
   답변 한국어율 speed 0% · balanced 0.6% · quality 3.1%. 소스는 대부분 한국어인데 **최종 답변 언어가 질의 언어를 따라가지 않음**. (UI 채팅 경로 스크린샷은 한국어였음 → `/api/search`(APISearchAgent)와 UI(chat route)의 writer 동작 차이 또는 모델 언어 일관성 문제로 추정. 별도 확인 권장.)

5. **balanced가 현재 유일하게 안정적인 실사용 모드.**
   속도(52s)·구조·소스 수 균형이 가장 낫고 실패가 없었음.

## 한계 및 주의

- **표본 크기**: balanced/quality는 각 1회, speed는 3회. SearXNG는 비결정적이라 회차별 편차가 큼(speed에서 이미 확인). 정밀 비교에는 모드별 다회 반복 필요.
- **엔드포인트**: 본 측정은 `/api/search`(프로그램 경로). UI 채팅 경로와 답변 언어 등 일부 동작이 다를 수 있음.
- **임베딩 선택**: `all-MiniLM-L6-v2`로 고정 측정. speed/balanced의 `similarity > 0.5` 필터는 임베딩 품질에 민감하므로, `mxbai-embed-large-v1` 등으로 바꾸면 한국어 결과 통과율이 달라질 수 있음.
- **품질 등급**은 객관 프록시(길이/구조/소스/언어) 기반의 정성 평가이며, 사실 정확성 자체를 검증한 것은 아님.

## 결론

> **speed는 '빠른 모드'가 아니라 '복원력을 전부 제거한 모드'다.** 실측 성공률 33%, 속도 이점 없음 → 현재 상태로 사용자 서비스 불가.
> **balanced**가 속도·안정성·근거 균형으로 실사용 기본값으로 적합.
> **quality**는 최고 품질이나 120초/타임아웃(524)·영어 응답 등 운영 리스크를 먼저 해결해야 함.
