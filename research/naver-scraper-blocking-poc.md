# 네이버 스크래퍼 차단 PoC — 편차/글로벌 유출의 진짜 원인

> 측정일: 2026-07-01
> 대상: https://search.vsvs.kr (OCI 도쿄, 운영과 동일 IP) 내부 SearXNG + 네이버 직접 요청
> 관련: [00-search-quality-benchmark.md](./00-search-quality-benchmark.md) finding #6 (원인 정정), [01-self-index-vs-live-fetch.md](./01-self-index-vs-live-fetch.md)

## TL;DR

> 벤치마크에서 본 **"실행마다 한국 소스 비율이 출렁이고 글로벌로 새는" 편차의 진짜 원인은 쿼리 언어가 아니라 "네이버의 스크래퍼 차단"이다.** 검색 1회가 네이버로 **10갈래 동시 요청(fan-out)** 을 쏘기 때문에, **질의 2번(≈20개 동시요청)** 만에 네이버가 서버 IP에 **HTTP 403 "access denied"** 를 반환하고, 네이버 계열 엔진 10개가 **약 3분간 전멸**(자동 회복)한다. 동시 사용자가 조금만 늘면 회복 즉시 재트립되어 **사실상 상시 블랙아웃** → 결과가 google로 붕괴 → "한국 검색"이라는 제품 정체성이 무너진다. **스크래핑 자체가 문제가 아니라 "한 번에 동시에 때리는(동시 fan-out burst)" 구조가 문제다.**

## 핵심 결론 3가지 (필수)

### 1. 네이버가 access denied를 반환하는 조건 = **짧은 시간 내 동시 요청 수(순간 동시성)**
- **단일·순차 요청**(0.4초 간격, 단일 엔드포인트 20회) → **전부 HTTP 200 정상**. 차단 안 됨.
- **SearXNG 질의 2번** → 차단. SearXNG 질의 1건은 네이버 계열 엔진 **10개를 동시에** `search.naver.com`으로 쏘므로, 2질의 = **수초 내 약 20개 동시요청** → 네이버 봇탐지가 **HTTP 403 "access denied"** 반환.
- 실측 임계: **10개 동시(1질의)는 통과, ~20개 동시(2질의)에서 차단.**
- 즉 조건은 "총 누적 요청량"이 아니라 **"한 IP에서 같은 순간 몰리는 동시 요청 수"**.

### 2. SearXNG 블랙아웃 기간 = **실측 약 3분, 자동 회복** (코드 명목값 24h와 다름)
- **코드 명목값**(`settings_defaults.py`): `access denied`(HTTP 402/403) → `SearxEngineAccessDenied` = **86,400초 = 24시간**.
- **실측 현실:** 트립 후 **약 3분(132~198초 사이) 만에 10개 엔진 전부 자동 회복.**
- 해석: 24h가 안 걸렸다는 건 **네이버 커스텀 스크래퍼가 24h짜리 typed 예외를 SearXNG에 전파하지 않는다**는 뜻(차단 페이지를 받아도 짧은 밴/빈 결과로 처리). 따라서 실제 블랙아웃 길이를 지배하는 건 **네이버 쪽 IP 쿨다운(~2~3분)**.
- ⚠️ **"3분이면 회복"이 안심거리가 아님:** 동시 사용자가 몇 명만 돼도 회복 즉시 누군가의 질의가 또 ~20개 동시요청을 쏴 **재트립** → **사실상 상시 블랙아웃**. 무료 서비스에서 트래픽이 붙을수록 만성화.

### 3. 정밀 원인 = 스크래핑 자체가 아니라 **"한 번에 동시에 때리기"(동시 fan-out 버스트)**
- **Fan-out** = 입력 하나가 여러 갈래로 **동시에** 퍼져 나감. 사용자 검색 1번 → SearXNG가 활성 엔진 전부에 동시 요청.
- **문제:** `naver`, `naver blog`, `tistory` + 커뮤니티 7개(`korean_site_search`: dcinside/clien/ruliweb/theqoo/ppomppu/bobaedream/instiz) = **총 10개 엔진이 전부 같은 목적지 `search.naver.com`을 같은 순간 두드림.** 사용자 눈엔 검색 1번이지만 네이버 입장에선 "한 IP에서 순간 10개".
- **버스트(burst)** = 짧은 시간에 몰리는 요청 다발. 2질의면 ~20개가 수초 내 → 네이버가 "사람이 아니라 봇/공격"으로 판정 → 403.
- 순차로 하나씩 하면 네이버도 허용(PoC Part B에서 증명). → **문제는 스크래핑이 아니라 "동시성"**.

```
사용자 질의 1개
   └─ SearXNG fan-out (동시)
        ├─ naver ────────┐
        ├─ naver blog     │
        ├─ tistory        │  10개 엔진이 전부
        ├─ dcinside       │  search.naver.com 을
        ├─ clien          │  "같은 순간" 두드림
        ├─ ruliweb        │  → 2질의(~20동시)에서 403
        ├─ theqoo         │
        ├─ ppomppu        │
        ├─ bobaedream     │
        └─ instiz ────────┘
        + google, bing, duckduckgo... (글로벌은 각자 다른 서버 → 안전, 그래서 살아남음)
```

## PoC 방법 & 원자료

OCI 도쿄 서버(운영과 동일 IP)에서 실행. 스크립트: `/tmp/naver_poc.py`, `/tmp/naver_recovery.py`, `/tmp/searx_probe.py`.

### 실험 A — SearXNG 반복 질의 시 죽는 엔진 (`unresponsive_engines` 관측)
```
[1] 결과 199개 | 네이버계열 10개 전부 alive
[2] 결과 199개 | 네이버계열 10개 전부 alive
[3] 결과  20개 | 네이버계열 0개  → 전부 'access denied'
[4~6] 결과 20개 | 'Suspended: access denied' (계속 죽어있음)
```

### 실험 B — 네이버 직접 요청(순차·단일) 20회
```
[1~20] HTTP 200, 결과블록 15개씩 정상  → 차단 안 됨
```
→ 순차·단일은 통과. (스크립트가 'captcha' 마커로 오탐했으나, 네이버 정상 페이지 HTML에도 해당 문자열이 있어 오탐. 실신호 `blocks=15`는 성공을 의미.)

### 실험 C — 트립 임계 & 회복 시간 실측 (`naver_recovery.py`)
```
STEP1 현재상태:  네이버 10개 전부 alive (199개)
STEP2 트립:
  q#1: 199개, 네이버 10 alive
  q#2:  10개, 네이버  0  ── 'access denied' × 10   ← 2번째 질의에서 전멸
STEP3 회복(60s 간격 폴링):
  +66s  죽음 / +132s 죽음 / +198s 10개 전부 회복 ✅
```

### 코드 근거 (컨테이너 내부 SearXNG 소스)
- `searx/settings_defaults.py` `suspended_times`:
  | 실패 종류 | HTTP 트리거 | 정지 기간 |
  |---|---|---|
  | AccessDenied | 402/403 | 86,400s = **24h** |
  | Captcha | 캡차 | 86,400s = 24h |
  | TooManyRequests | 429 | 3,600s = 1h |
  | Cloudflare CAPTCHA | CF 챌린지 | 1,296,000s = 15일 |
  | reCAPTCHA | 503+recaptcha | 604,800s = 7일 |
  | 일반 실패 | (예외 없음) | `min(120,5)` = 5s |
- `searx/search/processors/abstract.py` `suspend()`: 예외가 기간을 지정하면 그 값, 아니면 5초. → 명목상 403이면 24h지만, 실측은 ~3분(위 해석 참고).
- 앱 호출부 `src/lib/searxng.ts`: **engines·language 미지정 + 10초 타임아웃** → 기본 엔진 전체로 동시 fan-out.

## 처방 (원인별)

1. **동시성 억제(1순위).** 커뮤니티 7개 + naver/blog/tistory가 전부 `search.naver.com`이므로 **동시 fan-out을 직렬화/rate-limit**(엔진 간 간격, 동시 1~2개)하면 트립을 크게 낮춤. 근본 처방.
2. **콘텐츠 캐시**([01 문서]) — 같은 질의 재스크래핑 회피 → 네이버 히트 수 자체 급감.
3. **네이버 공식 오픈 API**(블로그/뉴스 검색) 도입 — 스크래퍼 일부를 정식 API로 대체 → 403 리스크 제거(무료 쿼터).
4. **엔진 통합.** 커뮤니티 7개를 개별 `site:` 스크래핑 대신 한 번의 네이버 검색으로 묶어 요청 수 자체를 축소.
5. **관측.** SearXNG 응답의 `unresponsive_engines`를 로깅해 네이버가 언제 죽는지 모니터링.
6. (증폭 요인) 쿼리 한국어화 + 한국어 임베딩 교체 + 앱 10초 타임아웃 상향.
