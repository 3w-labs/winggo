# 의사결정: 윙고(Winggo)에 자체 색인이 필요한가? 글로벌 1군과 어떻게 차별화하나

> 작성일: 2026-06-30
> 맥락: 윙고 = Perplexica/Vane 포크 기반 한국형 AI 검색엔진. 무료 서비스. SearXNG에 네이버/한국 커뮤니티 커스텀 엔진을 붙여 운영 중.

---

## Q1. 한국형 Perplexity를 만들려면 자체 색인(크롤링 봇으로 사전 수집)이 필요한가? 아니면 라이브 스니펫 기반 fetch가 나은가?

**A. 자체 범용 색인은 만들지 않는다. "라이브 fetch + 캐시" 하이브리드가 정답이다.**

특히 **무료 서비스**라는 제약에서 자체 색인은 거의 자살골이다.

### 자체 색인을 만들면 안 되는 이유 (제약 기준)

1. **비용이 무료 서비스와 정면 충돌.** 한국 웹을 크롤+저장+임베딩으로 색인하면 크롤러 인프라·스토리지·벡터DB·재색인 비용이 월 수백~수천만 원 단위. 무료 서비스가 감당할 구조가 아니다. (Perplexity는 대규모 투자를 받아 수천억 페이지 색인을 굴린다.)
2. **이미 한국 최고의 색인이 존재 = 네이버** 한국 블로그·카페·커뮤니티 콘텐츠는 구글보다 네이버가 압도적으로 잘 색인한다. 그리고 윙고는 이미 그걸 쓰고 있다(naver_web / naver_blog / korean_site_search). 자체 크롤러를 만든다는 건 *네이버 색인을 더 못한 품질로 재발명*하는 것.
3. **법적·차단 리스크.** 한국 사이트 대량 크롤링은 robots.txt·ToS·IP 차단 문제를 키운다. 반면 사용자 질의 시점에 상위 몇 개 URL만 fetch하는 건 훨씬 방어 가능하다.

> 핵심: **윙고의 진짜 색인은 네이버다.** 그걸 공짜로 빌려 쓰는 게 경쟁력이지, 직접 색인을 짓는 게 아니다.

## Q2. 그럼 순수 라이브 스니펫 fetch면 끝인가?

**A. 아니다. 순수 스니펫-only는 할루시네이션 위험 + 매번 본문 fetch는 느림. 빠진 건 "캐시"다.**

무료 서비스에서 속도와 비용을 동시에 잡는 레버는 "색인"이 아니라 **"캐시"**다. 윙고는 이미 **Postgres + Redis가 떠 있어** 캐시 인프라가 준비돼 있다.

### 추천 아키텍처

```
질의
 ├─ ① 시맨틱 캐시 (query→answer)  ── Redis, TTL 짧게
 │     히트 → 즉답 (가장 빠름, 비용 0)
 │
 └─ 미스 → SearXNG(네이버/커뮤니티 엔진)으로 후보+스니펫 획득
            ├─ ② 콘텐츠 캐시 (url→추출본문) ── Postgres, TTL 1~7일
            │     히트한 URL은 fetch 스킵
            └─ 미스한 상위 3~5개만 라이브 fetch → 추출 → 캐시에 저장
```

이것이 **"가난한 자의 색인(poor-man's index)"** 이다. 전체 웹을 미리 긁는 대신, 실제 사용자가 본 것만 사후에 캐시해 색인처럼 재사용한다. 무료 서비스는 질의가 인기 토픽(트렌드·이슈·연예·맛집)에 몰리므로 캐시 적중률이 높아 비용·지연이 급감한다.

### 시맨틱 캐시 vs 콘텐츠 캐시 — 무엇이 다른가

둘 다 "캐시"지만 **저장하는 것**과 **재사용 단위**가 완전히 다르다.

- **시맨틱 캐시** = "**질문 → 최종 답변**" 통째로 저장 (파이프라인 전체를 건너뜀)
- **콘텐츠 캐시** = "**URL → 그 페이지 본문**" 저장 (fetch/추출 단계만 건너뜀)

| | ① 시맨틱 캐시 | ② 콘텐츠 캐시 |
|---|---|---|
| **키(Key)** | 질의(query) — 의미 기반 | URL — 정확히 일치 |
| **값(Value)** | LLM이 만든 최종 답변 | 그 URL에서 추출한 본문 텍스트 |
| **건너뛰는 단계** | 검색·fetch·LLM **전부** | fetch + Readability 추출만 |
| **적중 시 효과** | 즉답 (비용 0, LLM 호출 X) | LLM은 돌지만 크롤링은 스킵 |
| **저장소** | Redis (휘발성, 빠름) | Postgres (영속, 큼) |
| **TTL** | 짧게 (몇 분~시간, 답이 금방 낡음) | 길게 (1~7일, 본문은 잘 안 변함) |
| **공유 단위** | 같은 질문한 유저끼리 | 같은 URL을 본 모든 질문끼리 |

**왜 "의미 기반(semantic)"인가:** 일반 캐시는 키가 글자 그대로 똑같아야 적중하지만("서울 날씨" ≠ "오늘 서울 날씨 어때?"), 시맨틱 캐시는 질의를 임베딩(벡터)으로 바꿔 의미가 충분히 비슷하면(코사인 유사도 > 임계값) 같은 답을 재사용한다. 예: `"아이폰 16 살까?"` ≈ `"아이폰 16 구매 추천?"` → 같은 캐시 히트.

**둘의 협력 예시:**
- 유저 A "fmkorea 그래픽카드 추천" → 둘 다 미스 → 5개 fetch(콘텐츠 캐시에 저장) → LLM 답변(시맨틱 캐시에 저장)
- 유저 B 30분 뒤 "그래픽카드 뭐가 좋아?"(의미 유사) → ① 시맨틱 캐시 **히트** → 즉답, 검색·LLM 안 돌림
- 유저 C "fmkorea 그래픽카드 vs CPU 가성비"(질문은 다름) → ① 미스, 하지만 일부 URL이 겹침 → ② 콘텐츠 캐시 **히트** → 그 URL은 fetch 스킵, 새 URL만 fetch 후 LLM 재생성

**정리:** 시맨틱 캐시는 "답 자체"를 아껴 **속도·LLM 비용**을 줄이고(답이 빨리 낡으니 TTL 짧게), 콘텐츠 캐시는 "읽어온 본문"을 아껴 **크롤링 비용·지연**을 줄인다(본문은 잘 안 변하니 TTL 길게). 둘은 계층(layer)이라 효과가 곱해진다 — 시맨틱이 "완전 중복 질문"을 막고, 콘텐츠가 "다른 질문이지만 같은 소스"를 아껴준다. 무료 서비스 관점에선 **시맨틱 캐시가 비용 절감 1등**(LLM 호출 제거), **콘텐츠 캐시가 지연 단축 1등**(무거운 Playwright fetch 제거)이다.

## Q3. 백그라운드 봇으로 캐시를 미리 채워야 하나? (콜드스타트 문제)

**A. "콘텐츠 캐시 워밍 봇"은 0명일 때 별로다(lazy fill이 정석). 하지만 "트렌딩 쿼리 워머(= Perplexity Discover 방식)"는 런칭 1순위 기능이 될 수 있다. 범용 링크추적 크롤러는 절대 금지.** *(2026-06-30, 4갈래 추가 조사로 결론 갱신 — 이전의 "v2 이후, 불필요"는 너무 보수적이었음)*

### 왜 순수 "콘텐츠 캐시 워밍 봇"은 0명일 때 별로인가
- 콘텐츠 캐시의 키는 **URL**이고, URL은 쿼리에서 파생된다. 사용자가 0명이면 **어떤 URL이 필요할지 예측할 방법이 없다.** 아무 URL이나 미리 긁으면 → 아무도 안 찾는 페이지 캐싱(낭비) + origin 부하 + 금방 stale.
- 교과서 답은 **lazy fill(cache-aside)**: 첫 요청이 각 키를 자연스럽게 채운다. (AWS 캐싱 가이드)
- **빈 콘텐츠 캐시는 "고장"이 아니다.** 첫 유저가 평소 라이브-fetch 지연(=baseline)을 한 번 낼 뿐, 그 순간 캐시가 채워진다. 캐시는 속도 최적화지 정상동작 조건이 아니다.

### 진짜 콜드스타트는 캐시가 아니라 "빈 홈페이지(engagement)"다
- 런칭 직후의 실제 문제는 "홈에 아무것도 없음 + 데모 질의가 느림 → 첫인상 나쁨" = **UX/engagement 콜드스타트**.
- 이걸 푸는 게 **Perplexity Discover**: 트렌딩 토픽마다 페이지를 **사용자가 묻기 전에 사전 생성**해 둔다(목적은 SEO가 아니라 cold-start/engagement).
- **"head는 prefetch, tail은 on-demand"는 정석 전략**(Zipf 법칙). Google 쿼리의 **~85%가 반복**, 상위 10% 쿼리가 트래픽 ~45%. → 인기 토픽만 미리 처리해도 적중률이 매우 높다.

> **결론(요약): 무엇을 미리 캐싱하나**
> - **Discover(고정 토픽 9개) = ✅ 전부 미리 캐싱이 최우선.** 집합이 고정·유한(bounded)이라 예측 가능 → 색인 함정이 아님.
> - **일반 검색창 쿼리 = 그냥 둔다(lazy fill).** 무한·예측 불가라 미리 못 채움, 첫 요청이 채운다.
> - 상세 설계는 [Discover 사전 캐싱 전략 문서](./02-discover-precache-strategy.md) 참고.

### 워밍 vs 색인 — 두 개념의 차이

둘 다 "데이터를 미리 준비"하지만 **대상 집합이 닫혀 있나(워밍) vs 열려 있나(색인)** 가 근본 차이다.

- **워밍(warming)** = 보여줄/물어볼 게 **이미 정해진 유한 목록**을 미리 데워두는 것 (캐시 채우기). → *아는 것을 빠르게.*
- **색인(indexing)** = 사용자가 **뭘 물을지 모르니** 웹을 최대한 긁어 검색 가능하게 저장 (DB 구축). → *모르는 것에 대비해 다 모으기.*

> 비유: **색인 = 도서관 짓기**(모든 책을 미리 사서 분류 — 무엇을 물어도 답하지만 비용 무한). **워밍 = 오늘 강연에 쓸 책 5권만 책상에 꺼내두기**(쓸 게 정해져 비용은 딱 그만큼, 끝나면 도로 꽂음).
>
> 윙고 대입: **네이버 = 도서관(색인)** → 빌려 쓰면 됨, 직접 지을 필요 없음. **Discover 사전 캐싱 = 워밍** → 토픽 9개가 정해져 있으니 그것만 미리 꺼내둠.

### 워밍(✅)과 색인(❌)의 경계 = bounded vs unbounded

| | 워밍 (해도 됨) | 색인 (함정) |
|---|---|---|
| 대상 | 고정된 N개 쿼리/URL (트렌드 리스트·사이트맵) | 발견되는 모든 페이지 |
| 확장 | 링크 안 따라감 | 프런티어 재귀 확장 |
| 비용 | 통제됨 (소규모 $5~50/월) | 무한 증가 |
| 목적 | 아는 것의 **속도** 최적화 | 모르는 질문 대비 **검색 기반** 구축 |
| 데이터 | 잠깐 쓰고 버림 (TTL·만료) | 영구 보관·갱신 (자산) |

→ **트렌딩 상위 N개 쿼리를 "기존 파이프라인(SearXNG→fetch→추출)"에 그대로 돌리는 것**은 bounded라서 안전하다. 별도 크롤러를 만드는 게 아니라 *이미 있는 검색 경로를 미리 실행*하는 것뿐. 이러면 콘텐츠/시맨틱 캐시가 자동으로 채워지고, 그 결과물이 홈 Discover 피드가 된다(일석이조). 함정은 "링크를 따라가며 무한 수집"하는 순간 시작된다 — 입구를 트렌딩 쿼리 리스트로 고정하면 그 선을 안 넘는다.

### 시맨틱 캐시 시딩도 정석
- 빈 시맨틱 캐시도 lazy fill이 기본이지만, **런칭 시 FAQ/예상 쿼리 ~수백~1000개를 미리 한 번 돌려 시드하는 건 권장 패턴**(Redis / Google Cloud 가이드). 데모 질의·랜딩 예시 질문을 시드하면 첫인상이 즉답.
- 시맨틱 캐시 전형 히트율 ~30%(RAG 18~60%), 워밍하면 초기 적중률이 크게 상승.

### 콜드스타트 대응 권고 (요약)
1. **콘텐츠 캐시 = lazy fill 기본** + stampede 방지(singleflight + stale-while-revalidate). 0명일 때 URL-워밍 봇 ❌.
2. **런칭 시드**: 데모/FAQ 질의 수십~수백 개를 파이프라인에 1회 돌려 캐시 + 홈 피드 시드.
3. **트렌딩 워머(Discover) = O, 단 bounded.** 매일 네이버 데이터랩/뉴스 + 구글 트렌드 상위 토픽 N개를 **기존 검색 파이프라인**에 돌려 캐시 워밍 + 홈 Discover 피드 생성. cold-start와 빈 UX를 동시 해결.
4. **범용 링크추적 크롤러 = 절대 ❌** (색인 함정).

## Q4. 글로벌 1군(Perplexity, ChatGPT, Gemini)과 어떻게 차별화하는가?

**A. 차별화는 "색인"이 아니라 한국 콘텐츠 커버리지 + 한국어 리랭킹 + 캐시에서 나온다.**

글로벌 1군은 전부 자체 색인 + passage 추출로 본문을 읽는다(아래 시장조사 표 참조). 윙고는 그 게임에 정면으로 못 들어간다. 대신 그들이 약한 곳을 친다.

1. **커뮤니티 콘텐츠 = 윙고의 해자.** dcinside·fmkorea·theqoo·뽐뿌·보배드림 검색을 이미 붙인 것이 핵심. Perplexity/ChatGPT/Gemini가 약한 "한국 사람들의 실제 후기·논쟁·꿀팁"을 잡는다. 본문 추출 품질(댓글 포함 여부 등)을 다듬는 게 색인보다 가치가 크다.
2. **한국어 리랭킹.** 코사인 유사도 필터만 쓰지 말고 한국어 임베딩/리랭커(BGE-m3, multilingual-e5, KURE/ko-sroberta 등)로 "어떤 3개를 읽을지" 정확도를 올린다. 본문 fetch 개수를 줄이며 품질을 지키는 핵심.
3. **fetch 경량화.** 지금 모든 페이지를 Playwright(헤드리스 크롬)로 여는데 무겁다. 정적 페이지는 가벼운 HTTP fetch + Readability, JS 렌더가 필요할 때만 Playwright로 분기 → 속도·서버비 절감. 상위 N개는 병렬 fetch.
4. **모드 균형 이동.** speed=스니펫(즉답), **balanced=스니펫+상위 3개 본문(기본 권장)**, quality=깊게. 현재 balanced가 speed와 같이 스니펫-only인 걸 격상하는 게 1순위.

## 부록: 시장조사 요약 (2026-06-30, 6갈래 병렬 조사)

상용 AI 검색엔진 중 "색인 스니펫만으로 끝내는" 곳은 사실상 없다. 두 패턴으로 갈린다:
- **사전 크롤링 색인 + 질의시 passage 검색**: Google, Perplexity, Bing, ChatGPT (자체 색인 보유)
- **자체 색인 없으면 질의 시점에 상위 N개 URL 실시간 fetch**: 오픈소스 클론, Brave LLM Context API, Kagi Assistant, You.com

### 오픈소스 클론 (윙고와 같은 처지 = 자체 색인 없음)

| 프로젝트 | 본문 fetch | 방식 |
|------|:---:|---|
| Perplexica/Vane | quality만 ✅ | Playwright+JSDOM+Readability, speed/balanced는 스니펫 |
| Morphic | advanced만 ✅ | JSDOM 크롤 / fetch툴은 Jina Reader→Tavily 폴백 |
| Khoj | 옵션 ✅ | Firecrawl/Olostep/BeautifulSoup |
| llm-answer-engine | 항상 ✅ | Cheerio→청크→OpenAI 임베딩→top-k (정석 RAG) |
| openperplex | ✅ | 시맨틱 청킹 + Jina 리랭크 |
| Farfalle / lepton / scira(기본) | ❌ | 스니펫만 |

→ 자체 색인이 없는 진지한 엔진은 거의 다 실시간 본문 fetch를 한다. 스니펫-only로 남은 건 가벼운 데모성 프로젝트들.

### RAG 베스트프랙티스 합의
- 스니펫은 단순 사실 조회엔 충분하나, 뉘앙스·수치·스펙 질의에서 정보 누락·할루시네이션 증가.
- 표준 파이프라인: search → 상위 N개(3~5)만 본문 fetch → 청킹(256~1024토큰, 15~25% 오버랩) → 리랭킹(50~100후보→top-k) → 인용 강제.
- 단, 본문을 무지성으로 다 넣으면 노이즈로 오히려 악화 → 리랭킹/필터링 필수.
- 비용/지연 완화: top-N만 읽기, 병렬 fetch, 캐싱, Reader API(Jina r.jina.ai, Tavily extract).
