# 네이버 공식 API vs 직접 스크래핑 — 비교·한도·왜 API인가

> 작성일: 2026-07-01
> 맥락: 윙고(Winggo) 한국 소스 확보 전략. [04-naver-scraper-blocking-poc.md](./04-naver-scraper-blocking-poc.md)에서 스크래핑의 동시 fan-out 차단(403, ~3분 블랙아웃)을 실측한 뒤, 그 극복책으로 공식 API 전환을 검토.
> 관련: [00-search-quality-benchmark.md](./00-search-quality-benchmark.md) · [01-self-index-vs-live-fetch.md](./01-self-index-vs-live-fetch.md)

## TL;DR

> **둘 다 초당 제한은 있다. 하지만 스크래핑의 제한은 "지뢰밭"(비공개·가변 임계 + 403 차단 + ~3분 블랙아웃 + 불법)이고, API의 제한은 "신호등"(공개·고정 10 QPS + 429 속도조절 + 초 단위 회복 + 합법)이다.** 그래서 API는 토큰버킷으로 페이싱하면 사실상 무중단으로 굴릴 수 있고 **3분 블랙아웃 문제가 사라진다.** 결론은 하이브리드: **네이버 자산(블로그·뉴스·웹·카페)=공식 API, 외부 커뮤니티(dc/fm/더쿠…)=구글 `site:`+저동시성 스크래핑+캐시.**

## 1. 네이버 검색 오픈 API 한도 (developers.naver.com)

| 구분 | 값 | 초과 시 |
|---|---|---|
| **일일 호출** | **25,000회/일** (Client ID당, 00:00 KST 리셋) | 호출 거부, 자정까지 |
| **초당 호출** | **약 10 req/sec** | **HTTP 429** Too Many Requests |
| 콜당 결과 | `display` 최대 **100건** | — |
| 페이지네이션 | 실질 **최대 ~1,000건/쿼리**(약 10페이지) | 이후 빈 결과 |
| **비용** | **완전 무료. 유료 상향 티어 없음** | 돈으로 늘리는 옵션 자체가 없음 |

### 한도는 "엔드포인트별"이 아니라 "Client ID 통합"
- 제한은 인증 자격(`X-Naver-Client-Id`) 단위로 걸린다. **블로그·카페·지식iN·뉴스·웹 검색이 전부 같은 버킷에서 차감**(엔드포인트별 별도 한도 아님). 환경(웹/앱)과도 무관하게 합산.
- 함의: 검색 1번이 블로그+뉴스+카페+웹+지식iN = 5개 엔드포인트를 동시 호출하면 **순간 10 QPS 중 5개를 한 번에 소모**. → **엔드포인트 합친 전체 QPS를 하나의 레이트리미터(≤10/초)로 관리**해야 함. (fan-out 문제는 API로 가도 따라오지만, 벌칙이 다름 — 아래 3장)

### 늘리는 방법 (비용)
1. **캐싱으로 배가($0)** — 반복 질의 히트 시 API 미사용. 한국 트래픽 Zipf(반복 ~85%) → 실효 천장 크게 상승.
2. **콜 수 절약** — 검색당 필요한 엔드포인트만.
3. **쿼터 증액 요청** — 정식 서비스면 네이버에 상향 문의(무료, 케이스별 승인).
4. **앱 다중 등록**(회색지대) — Client ID 여러 개 라운드로빈으로 배수, 단 ToS 리스크.
5. **유료 3rd-party**(최후) — SerpApi·Bright Data 등 유료 Naver SERP API(1,000검색당 과금). 무료 서비스엔 부담.

> 신뢰도: 일일 25,000 합산 = 공식 확인(고신뢰). 초당 ~10 = 커뮤니티 관측치(중간) — 실제 키로 부하 테스트 권장.

## 2. 장단점 비교

| 축 | 공식 API | 직접 스크래핑(현재) |
|---|---|---|
| 차단/안정성 | ✅ IP 차단·동시성 403 **없음** | ❌ 순간 동시성에 403, ~3분 블랙아웃(상시화) |
| 합법성/ToS | ✅ 네이버가 허가한 정식 경로(출처표기 의무) | ❌ ToS 위반 소지, 회색지대 |
| 유지보수 | ✅ 안정적 JSON 계약 | ❌ HTML(`fds-web-doc-root`) 바뀌면 깨짐 |
| 속도 | ✅ JSON, 파싱·타임아웃 부담 적음 | ❌ 220KB HTML 파싱, 10초 타임아웃 위험 |
| 커버리지 | ⚠️ 네이버 자산만(블로그·뉴스·웹·카페·지식iN·쇼핑) | ✅ 네이버 통합검색 전체(+`site:`로 외부 커뮤니티) |
| **커뮤니티(dc/fm/더쿠/클리앙…)** | ❌ **아예 없음**(네이버 자산 아님) | ⚠️ `site:`로 가능하나 차단됨 |
| 쿼터 | ⚠️ 25k/일·10 QPS 하드 천장 | ✅ 형식적 상한 없음(현실 상한=차단) |
| 데이터 필드 | ✅ 정제 필드(제목·링크·요약·작성일 등) | ⚠️ 광고·잡요소 섞인 HTML |
| 결과 일치성 | ⚠️ API 색인이 실제 naver.com과 다를 수 있음 | ✅ 사용자가 보는 SERP와 동일 |
| 셋업 | ⚠️ Client ID/Secret 등록 필요 | ✅ 불필요 |

## 3. 핵심 질문 — "둘 다 초당 제한 있는데 왜 API가 나은가? API엔 3분 블랙아웃이 없나?"

**답: 있다(초당 제한). 하지만 제한의 종류와 초과 벌칙이 근본적으로 다르며, API엔 3분 블랙아웃이 없다.**

### 403(차단) vs 429(속도조절)

| | 직접 스크래핑 | 공식 API |
|---|---|---|
| 초과 시 응답 | **403 access denied** | **429 too many requests** |
| 성격 | 안티봇/차단 ("넌 봇, 접근 금지") | 레이트리밋 ("너무 빨라, 천천히") |
| 회복 | **~3분 블랙아웃**(엔진 suspend 겹침), 최악 24h | **~1초**(짧은 백오프면 즉시 재호출) |
| 관계 | 적대적(네이버가 막으려 함) | 협조적(쓰라고 열어준 것) |
| 임계값 | 비공개·가변(언제든 강화·캡차 추가) | 공개·고정(10/초·25k/일) |

### 왜 API엔 3분 블랙아웃이 없나 (3가지)
1. **429는 벌이 아니라 신호.** 403은 "어뷰저 → 문 잠금"(징벌적·suspend 연쇄), 429는 "이번 초 초과 → 다음 초에" (즉시 해소). 수 분 블랙아웃 개념 자체가 없음.
2. **API 한도는 알고 있어서 애초에 안 넘길 수 있다.** 공개된 고정값(10/초)이라 **토큰버킷으로 9/초 페이싱하면 429조차 안 남.** 스크래핑은 임계가 비공개·적응형이라 조심해도 어디서 걸릴지 모르고, 네이버가 언제든 더 조임.
3. **벌칙의 비대칭.** 스크래핑=한 번 넘으면 몇 분(최악 24h) 전멸. API=넘으려는 요청이 큐에서 몇 ms 대기. 같은 "초당 제한"이어도 초과 비용이 하늘과 땅.

### 비유
- **스크래핑 = 무단침입.** 걸리면 몇 분~하루 출입금지, 언제 걸릴지 모르고 경비가 점점 깐깐.
- **API = 회원제 출입증.** "시간당 X번" 명시, 초과하면 "잠깐만요" 하고 줄 세울 뿐 쫓아내지 않음. 규칙대로면 아예 안 걸림.

> 정직한 단서: 동시성 관리는 API로 가도 필요(10 QPS 순간초과 시 429). 하지만 스크래핑은 "관리해도 언제 403날지 모르고 벌이 무거운" 반면, API는 "관리하면 429조차 안 나고 나도 즉시 회복". **관리 난이도와 실패 비용이 다르다.**

## 4. 결론 — 택일이 아니라 하이브리드

> **네이버 자산(블로그·뉴스·웹·카페·지식iN) = 공식 API로** (차단 제거·속도·합법·안정). **외부 커뮤니티(dc/fm/더쿠/클리앙/뽐뿌/보배/인스티즈) = 구글 `site:`(현 fmkorea 방식) + 저동시성 스크래핑 + 캐시로.**

- API의 "커뮤니티 공백"을 스크래핑이 메우고, 스크래핑의 "차단 리스크"는 소수 호스트로 국한 + 동시성 캡·캐시로 통제.
- 윙고의 차별화(커뮤니티 해자)는 API로 안 되므로 스크래핑을 완전히 버리진 못함 → **동시성만 길들이는 것**이 관건.
- 어느 경로든 공통 원칙: **fan-out을 통합 레이트리미터로 다스린다**(API는 10 QPS 버킷, 스크래핑은 호스트당 동시 1~2 + 캐시).
