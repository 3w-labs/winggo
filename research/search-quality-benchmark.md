# 검색 품질·속도 벤치마크 (baseline 측정)

> 측정일: 2026-07-01
> 대상: https://search.vsvs.kr (운영 중인 라이브 서비스)
> 목적: 최적화 **이전** baseline 확보 — ① 속도(지연) ② 한국 콘텐츠(커뮤니티·블로그) 참조 비중.
> 관련: [01-self-index-vs-live-fetch.md](./01-self-index-vs-live-fetch.md) · [02-discover-precache-strategy.md](./02-discover-precache-strategy.md)

## TL;DR (한 줄)

> **"speed"는 느리고(27s) 절반이 검색조차 안 하며, "quality"만 한국 커뮤니티를 제대로 참조하지만 너무 느려(72s, 2건은 타임아웃) 실사용 불가. balanced는 소스의 46%가 글로벌로 새고 커뮤니티는 거의 안 씀. 근본 원인은 검색이 네이버/커뮤니티 엔진을 타깃하지 않고 SearXNG 기본(글로벌) 엔진으로 나가기 때문.**

## 측정 방법

- **엔드포인트:** `POST /api/search` (`stream:false` → `{message, sources}` 반환).
- **모델:** 채팅 = Grok `grok-4.20-0309-non-reasoning` (xAI), 임베딩 = 로컬 Transformers `all-MiniLM-L6-v2`. (서비스 실제 설정 그대로)
- **sources 파라미터:** `["web","discussions"]` (웹 + 커뮤니티 활성).
- **질의 12개 × 3모드(speed/balanced/quality) = 36 호출.** 카테고리: 커뮤니티형 5, 블로그형 3, 정보·뉴스형 4 (전부 한국어).
- **분류:** 각 소스 URL의 호스트를 커뮤니티(dcinside/fmkorea/theqoo/ruliweb/ppomppu/clien/bobae/instiz…), 블로그(blog.naver.com/tistory/brunch…), 뉴스·포털(naver/daum/언론사), 기타 .kr, 글로벌로 분류.
- **"인용" 측정:** 답변 본문의 `[n]` 마커를 소스 인덱스에 매핑해, *실제로 답변에 쓰인* 소스의 국적 구성도 별도 집계.
- ⚠️ **1회 실행**이라 실행 간 편차가 큼(아래 참고). 경향 파악용 baseline이지 정밀 수치는 아님.

## 발견 사항

### 1. "speed" 모드가 한국 정보성 질의에서 검색을 아예 안 한다 (할루시네이션 위험)
- speed 12건 중 **5건(42%)이 소스 0개**: `2026년 최저임금`, `전세 계약 주의사항`, `청년도약계좌 조건`, `종합소득세` 등 **사실이 중요한 한국 정보 질의를 LLM 기억만으로 답변**.
- Grok의 파라메트릭 지식은 한국 제도·수치에 최신성이 없어 → **틀린 값을 그럴듯하게 답할 위험**. 검색 기반 서비스의 존재 이유와 배치됨.

### 2. "speed"는 이름값을 못 한다
- 평균 27s, 최대 38s. 검색을 안 한 질의도 18~26s. 사용자 체감상 "빠른" 모드가 아님.

### 3. "quality"만 한국 커뮤니티를 제대로 참조하지만 실사용 불가
- 커뮤니티 소스가 quality에 20개(모드 소스의 41%) 몰림 — dcinside/fmkorea/theqoo 등 **한국 커뮤니티는 quality에서만 의미 있게 등장**.
- 그러나 평균 72s, **2건 타임아웃(524)**. 앞단 프록시(Caddy)나 게이트웨이가 ~125s에서 끊어 **사용자에게 빈 응답**. 품질은 좋지만 못 씀.

### 4. "balanced"는 소스의 46%가 글로벌로 샌다
- balanced 검색소스 59개 중 **글로벌 27개(46%)** — reddit·techradar·consumerreports 등. 한국어 질의인데 영어권 소스로 답을 구성.
- 커뮤니티는 2개(3%)뿐. 즉 balanced는 "한국 커뮤니티를 우선 참조"와 거리가 멂.

### 5. 카테고리별: 정보·블로그 질의일수록 글로벌로 샌다 (balanced+quality 합산)

| 질의 유형 | 커뮤 | 블로그 | 뉴스 | 기타KR | 글로벌 | KR% |
|---|---:|---:|---:|---:|---:|---:|
| 커뮤니티형(후기 등) | 16 | 24 | 0 | 0 | 5 | **89%** |
| 블로그형(여행·맛집·코딩) | 5 | 12 | 0 | 0 | 18 | 49% |
| 정보·뉴스형(제도·세금) | 1 | 1 | 3 | 8 | 15 | 46% |

→ **"후기/실사용" 뉘앙스 질의**는 한국 소스를 잘 잡지만(89%), **정보성·방법론 질의**는 절반 이상 글로벌로 샌다(파이썬 문서는 영어, 제도 질의는 글로벌 일반).

### 6. 실행 간 편차가 크다 (비결정성)
- 사전 probe에서 같은 `갤럭시 S24`(balanced)가 **소스 37개 대부분 글로벌**로 나왔는데, 벤치마크 실행에선 **소스 1개 커뮤니티**로 나옴.
- 원인 추정: 리서처 LLM(Grok)이 검색어를 **한국어로 뽑으면** 네이버/커뮤니티가 잡히고 **영어로 뽑으면** 글로벌이 잡힘 → **쿼리 언어의 비결정성이 소스 국적을 좌우**.

### 7. 인용은 검색 구성에 비례
- citedKR%가 retrievedKR%와 거의 동일(예: quality 78%→79%). LLM이 한국 소스를 **특별히 더/덜** 인용하지 않음 → 국적 편향은 **인용 단계가 아니라 검색·수집 단계에서 결정**됨. 고칠 지점이 명확.

## "검색 스킵"이란 무엇이고, 왜 발생했나

### 정의
- 이 벤치마크에서 **"검색 스킵" = API 응답의 `sources` 배열이 0개인 호출**을 뜻한다. 즉 그 질의에 대해 **웹 검색 결과가 하나도 답변에 반영되지 않은** 경우.
- 검색 기반 서비스인데 근거 없이 LLM(Grok) 기억만으로 답한다는 뜻 → **출처 없음 + 할루시네이션 위험**.

### 원인은 두 가지 (임베딩은 그중 하나에만 관여)

**원인 A — 분류기 LLM의 `skipSearch` 판단 (임베딩 무관)**
- 검색 전에 분류기(Grok)가 "검색이 필요한가?"를 먼저 정한다. `src/lib/prompts/search/classifier.ts`:
  > *"Set skipSearch to true if the query is straightforward, factual, or can be answered based on general knowledge."*
- Grok이 `2026년 최저임금`, `종합소득세 신고 방법` 같은 걸 **"factual/일반상식"으로 오판** → `skipSearch=true` → 웹 검색 액션 자체가 비활성(`webSearch.ts` `enabled: skipSearch===false`) → 소스 0개.
- 한국 제도·수치는 "일반상식"이 아니라 최신 검색이 필요한데 **분류기가 오분류**한 것. LLM 판단 문제지 임베딩과 무관.

**원인 B — 임베딩 유사도 필터로 전부 탈락 (임베딩이 진범 ✅)**
- 검색을 **했는데도** 0이 되는 경로. `src/lib/agents/search/researcher/actions/search/baseSearch.ts:74`:
  ```js
  .filter((c) => c.metadata.similarity > 0.5);
  ```
- 스니펫을 임베딩해 쿼리와 코사인 유사도 **0.5 미만이면 전부 버린다.** 그런데 임베딩 모델이 **`all-MiniLM-L6-v2`(영어 중심 소형, 한국어 약함)** → 실제로 관련 있는 한국어 스니펫도 유사도가 낮게 찍혀 0.5를 못 넘고 **전멸** → 소스 0개.
- 임베딩 호출이 **에러**나면 fallback으로 similarity=1을 줘 다 통과시키지만, **"낮은 점수"는 조용히 필터링**된다 → 약한 모델이 좋은 한국 결과를 소리 없이 버림.

### 왜 speed 모드에서만 유독 심한가 (42% vs 8% vs 10%)
- 분류기(`skipSearch`)는 **모드와 무관하게 1번** 실행 → 이것만이면 세 모드 skip률이 같아야 하는데 크게 다르다. 차이의 범인은 **원인 B**:
  - **speed** = 검색 1회 + 쿼리 소수 → 그 한 번의 결과가 0.5 필터에 다 걸리면 **바로 0**.
  - **balanced/quality** = 검색 여러 번 + 쿼리 여러 개 누적 → 하나라도 0.5를 넘으면 살아남아 **0 될 확률이 낮음**.
- 즉 speed의 높은 0-source율 = **A(분류기 오판) + B(임베딩 필터 전멸)가 겹친 것**, 특히 B가 speed에서 치명적.

### 처방

| 원인 | 무엇 | 임베딩? | 처방 |
|---|---|---|---|
| A | 분류기가 검색 불필요로 오판 | ❌ (LLM 판단) | classifier 프롬프트 수정 / 한국 정보성 질의는 skip 금지, 또는 balanced를 기본 모드로 |
| B | 검색했지만 유사도<0.5로 전멸 | ✅ (한국어 약한 모델) | **한국어 임베딩 모델**(BGE-m3, ko-sroberta 등)로 교체 + 임계값 완화/최소 하한 보장 |

> ⚠️ 한계: 본 벤치마크의 "검색 스킵 42%"는 **소스 0개**를 센 값이라 **A와 B를 합친 수치**다. 외부(API)에서는 "검색을 안 한 건지(A) vs 했는데 다 버린 건지(B)"를 구분할 수 없다. 분리하려면 서버 로그(분류기 출력)를 보거나 **필터를 잠깐 끄고 재측정**하면 된다.

## 근본 원인 (코드)

1. **검색이 한국 엔진을 타깃하지 않음.** `webSearch.ts`가 `executeSearch`에 **engines를 안 넘김**(`searchConfig` 미지정) → `searchSearxng`가 SearXNG **기본 엔진(구글/빙 등 글로벌 포함)** 으로 나감. 네이버/커뮤니티 커스텀 엔진이 우선되지 않고 글로벌과 섞임 → **글로벌 유출**. (`src/lib/agents/search/researcher/actions/search/webSearch.ts:98`)
2. **쿼리 생성 프롬프트가 영어 중심.** 예시가 `"Tesla latest news"`, `"GPT-5.1 features"` — 한국어 질의에도 영어 키워드를 유도 → 글로벌 소스 유입 + 편차. (`webSearch.ts` speed/balanced/quality 프롬프트)
3. **speed 모드의 과도한 skipSearch.** 분류기가 한국 정보성 질의를 "검색 불필요"로 판정 → 무근거 답변.
4. **quality 타임아웃.** 다중 검색 이터레이션 + Playwright 본문 스크래핑이 ~125s 게이트웨이 한도를 초과 → 524.

## 권고 (baseline → 개선 우선순위)

1. **검색을 한국 엔진으로 타깃.** `executeSearch`/`searchSearxng`에 `engines`(naver_web, naver_blog, korean_site_search 계열, fmkorea)를 명시 전달하거나 한국어 질의 감지 시 우선순위 부여 → 글로벌 유출 차단. **가장 효과 큰 1순위.**
2. **쿼리 생성 프롬프트 한국어화.** 예시를 한국어 키워드로 바꾸고 "한국어 질의는 한국어 검색어로" 지시 → 편차·유출 동시 감소.
3. **speed 모드 skipSearch 축소.** 최소한 한국 정보성 질의는 검색 강제(또는 balanced를 기본 모드로).
4. **quality 지연/타임아웃 해결.** 상위 N 병렬 fetch, Playwright 경량화(정적 페이지는 일반 fetch), 게이트웨이 타임아웃 상향. ([01 문서]의 fetch 경량화와 연결)
5. **커뮤니티 우선 랭킹.** 한국어 리랭커로 커뮤니티/블로그 소스에 가점 → "한국형 차별화"(커뮤니티 해자) 강화. ([01 문서] Q4와 연결)
6. **재측정.** 위 수정 후 동일 벤치마크(`scratchpad/bench.py`)를 재실행해 before/after 비교. 편차 때문에 **모드당 3회 반복 평균** 권장.
