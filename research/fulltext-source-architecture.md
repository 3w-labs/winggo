# 본문 기반 글감 수집 아키텍처 — 제안 배경·문제해결·다관점 평가

> 작성일: 2026-07-01

## TL;DR

> **스니펫이 아니라 "댓글 포함 본문"을 각 커뮤니티에서 직접 가져오는 구조로 간다.** 10대 커뮤니티는 각 사이트 직접 크롤(본문+댓글), 네이버 블로그는 공식 API, 티스토리는 검색 페이지 직접 크롤. 검색 1건이 한 호스트에 10갈래로 몰리던 fan-out을 **11개 독립 호스트로 분산**해 차단을 구조적으로 없애고, **본문+댓글**로 할루시네이션·얕음·영어편향을 동시에 잡는다. 세 관점(시니어 엔지니어·크롤링 전문가·타깃 유저) **만장일치 "기존보다 명확히 낫다".** 성패는 **지연 규율(top-N·병렬·데드라인)** 과 **커버리지 공백(네이버 카페·arca·인벤) 보강**에 달렸다.

## 1. 왜 이 방식을 제안했나 (문제의식)

지금까지의 실측(00·04·05·07)이 가리킨 결론:

1. **기존 구조의 소스는 사실상 "한 곳"이다.** SearXNG가 네이버 웹/블로그/티스토리+커뮤니티 7개를 전부 `search.naver.com` 스크래핑으로 처리 → 검색 1건 = **한 호스트에 10갈래 동시 요청(fan-out)** → 질의 2번에 네이버 403, ~3분 블랙아웃([04](./04-naver-scraper-blocking-poc.md)).
2. **목적지를 구글로 바꿔도 더 나빴다.** 구글 `site:`는 첫 질의부터 과반 차단, 12분+ 미회복, IP 전체 연쇄 다운([07](./07-google-api-vs-scraping.md)). → **문제의 본질은 "네이버냐 구글이냐"가 아니라 "한 곳에 동시 다발(fan-out)".**
3. **스니펫은 얕고 위험하다.** 결과가 SERP 미리보기(≤600자)뿐이라, 뒷광고 서두·어뷰징 블로그만 보고 답 → 할루시네이션. 게다가 한국어 질의인데 글로벌로 46% 유출([00](./search-quality-benchmark.md)).

**핵심 통찰:** 한국 커뮤니티에서 **진짜 정보는 본문과 "댓글"에 있다.** 그렇다면 SERP 스니펫을 긁을 게 아니라, **각 사이트에서 본문+댓글을 직접 가져오면**, 차단(호스트 분산)·품질(본문)·문화(댓글)를 한 번에 해결할 수 있다는 것이 제안의 출발점이다.

> 검증된 전제: 사용자가 **보배드림·클리앙·에펨코리아·디시인사이드 4곳에서 본문+댓글 파이썬 수집을 이미 검증**. 티스토리도 이 조사에서 `tistory.com/search`가 **서버렌더 HTML**로 결과를 담아 직접 크롤 가능함을 확인(내부 JSON 검색 API는 404, HTML 파싱 방식).

## 2. 제안 아키텍처

| 대상                                                                                           | 수집 방식                                                 | 색인/출처        | 도구                        |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ---------------- | --------------------------- |
| **10대 커뮤니티** (dcinside, fmkorea, theqoo, clien, ruliweb, ppomppu, bobaedream, instiz, +2) | 각 사이트 **직접 크롤**(검색/게시판 → 글 **본문 + 댓글**) | 각 커뮤니티 자체 | curl 우선 / CF면 Playwright |
| **네이버 블로그**                                                                              | **공식 오픈 API** (25k/일, 10 QPS)                        | 네이버           | HTTP(API)                   |
| **티스토리**                                                                                   | `tistory.com/search` **직접 크롤**(SSR HTML) → 글 본문    | 티스토리         | curl                        |

**설계 원칙**

1. **스니펫이 아닌 본문(+댓글)** 을 LLM에 공급 → 근거 있는 답, 할루시네이션↓.
2. **curl 우선, Playwright는 JS/Cloudflare 필요 시에만** → 무료 단일 서버(OCI ARM) 비용 통제.
3. **캐싱(Redis 시맨틱 + Postgres 콘텐츠)** 으로 반복 수집 회피, 속도 최적화.

## 3. 이 방식이 "기존의 어떤 문제"를 해결하는가 (핵심 규명)

조사 전체에서 실측한 문제 → 제안이 어떻게 푸는지의 1:1 매핑.

| #   | 기존(스니펫 + 단일호스트 fan-out)에서 실측된 문제                                           | 제안(본문 기반 + 호스트 분산)의 해결                                                                                                    |
| --- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **fan-out 차단**: 검색 1건이 `search.naver.com`에 10동시 → 2질의에 403, ~3분 블랙아웃([04]) | ✅ **호스트 분산**: 각 커뮤니티 직접 → 호스트당 요청 ~10→~1, **11개 독립 rate-limit 버킷**. "하나의 뜨거운 호스트 → 11개 차가운 호스트" |
| 2   | **구글 이전도 실패**: `site:` fan-out이 구글에선 더 심함(즉시 차단·IP 연쇄·12분+)([07])     | ✅ **SERP를 아예 안 거침**: 검색엔진 안티봇 표면(SERP)이 아니라 방어가 약한 **글 페이지**를 직접 침                                     |
| 3   | **스니펫 할루시네이션**: ≤600자 미리보기(뒷광고 서두)만으로 답([00·01])                     | ✅ **본문 전체 + 댓글**: 실구매가·팩트체크·베스트댓글(군중검증)까지 근거화                                                              |
| 4   | **글로벌 유출 46%**: 한국어 질의인데 영어 소스로 답 구성([00 finding #4])                   | ✅ **한국 소스 직접 지정**: 커뮤니티/블로그를 명시 수집 → 유출 없음                                                                     |
| 5   | **speed 검색 스킵 42%**: 근거 없이 LLM 기억으로 답([00 finding #1])                         | ✅ 본문 기반 파이프라인이 기본이라 무근거 답변 축소                                                                                     |
| 6   | **quality 125초 타임아웃**: 빈 응답([00])                                                   | ✅ **글로벌 데드라인 + 부분 반환**: 도착한 소스만으로 답, 느린 사이트가 전체를 막지 않음                                                |
| 7   | **속도**: 27~72초([00])                                                                     | ✅ **2단계(목록→top-N 본문) + 완전 병렬 + 캐시**로 단축                                                                                 |
| 8   | **네이버 마크업 의존 취약**: `fds-web-doc-root` 등 SERP HTML 바뀌면 붕괴                    | △ 사이트별 파서로 분산(단, 파서 유지보수는 새 비용 — 5장)                                                                               |

> 요약: **fan-out 차단(1·2)·품질(3·4·5)·응답성(6·7)** 을 동시에 푼다. 이는 지금까지 각 문서에서 따로 지적된 문제들을 **하나의 구조 변경으로 수렴 해결**하는 것이 핵심 가치다.

## 4. 다관점 평가 — 만장일치 "더 낫다" (3/3)

| 평가자          | 판정                       | 핵심                                                                                              |
| --------------- | -------------------------- | ------------------------------------------------------------------------------------------------- |
| 시니어 엔지니어 | **BETTER (clearly)**       | 1핫호스트→11콜드호스트로 차단 구조적 해소, 본문·댓글이 할루시네이션 근본 해결. 리스크는 관리 가능 |
| 크롤링 전문가   | **BETTER (올바른 방향)**   | 밴은 호스트당 부과 → 분산이 최대 승리. 글 페이지는 SERP보다 방어 약함                             |
| 타깃 유저       | **BETTER (marginal 아님)** | **댓글이 곧 해자.** 스니펫은 광고 서두, 진실은 본문·댓글. Perplexity/네이버가 못 하는 지점        |

### 왜 유저에게 "댓글"이 결정적인가

한국 커뮤니티에서 **본문=주장, 댓글=검증**이다. 잘못/광고 글은 몇 분 내 팩트체크·비추·정정되고, **베스트댓글은 사실상 군중검증된 결론**. 가성비·중고시세의 실제 숫자, 이슈의 다수의견·반론이 전부 댓글에 있다. → AI가 "광고를 요약"에서 "배심원단을 요약"으로 바뀐다. 이것이 제품의 해자.

## 5. 성립 조건 & 리스크 (그냥 되는 게 아님)

1. **지연 규율 (make-or-break).** 본문+댓글을 결과마다 순차 fetch하면 속도 붕괴. 필수:
   - **2단계 파이프라인**: ① 값싼 목록/검색으로 후보 랭킹 → ② **top-3~5만** 본문 fetch (인용 안 할 본문은 안 가져옴).
   - **완전 병렬** fetch + 호스트당 하드 타임아웃(약 2–3초) + **글로벌 데드라인(약 8초, 도착분만 반환)** + **소스 도착 순 스트리밍**.
2. **사이트별 안티봇 티어** (크롤링 전문가 검증):
   - **curl 가능**: bobaedream, ppomppu, instiz, **dcinside(`m.dcinside.com` 모바일)**, **tistory 검색(SSR)**.
   - **Playwright 필요(Cloudflare)**: **fmkorea(항상)**, clien·ruliweb·theqoo(대개).
   - **휴리스틱**: 응답에 CF 마커(`cf-mitigated`, `__cf_chl`, `challenges.cloudflare.com`) 또는 본문이 비정상적으로 작으면 → Playwright로 1회 승격. 웜 Playwright 풀은 JS 티어에만.
3. **호스트당 rate 규율 + 서킷브레이커.** 진짜 관건은 도구가 아니라 **속도**: 호스트당 0.5–1 req/s, 동시 2–3(절대 10 금지), `Retry-After` 준수, 403 반복 시 park 후 캐시 서빙.
4. **11개 파서 유지보수(새 비용).** 사이트 리디자인/댓글 AJAX로 몇 주마다 하나씩 깨질 수 있음. 완화:
   - **공통 `SourceAdapter` 인터페이스**(search→rank→fetch→parse)로 retry/cache/timeout 공유, 셀렉터만 사이트별.
   - **DOM보다 XHR/JSON 댓글 엔드포인트를 타깃**(더 안정), 셀렉터는 코드가 아닌 데이터파일로.
   - **파서별 스모크테스트/헬스체크**(본문 길이>N, 댓글>0)로 드리프트 경보. 깨진 파서는 "소스 스킵"으로 우아하게 강등, 전체 질의 실패 금지.
5. **법적 노출 관리.** 한국 판례는 *경쟁서비스용 대량복제·보호조치 우회·PII*를 처벌. → **URL+짧은 발췌만 저장(전문 아카이브 금지)**, robots.txt·`Retry-After` 준수, 사용자에게 **출처 인용**. 네이버 블로그는 공식 API라 무위험.

## 6. 커버리지 공백 (유저 관점 최대 약점 — 반드시 보강)

현재 10개 목록은 **남성·테크 편향**. 놓치는 곳:

- **네이버 카페(맘카페·중고나라 1,950만)** — 최대 공백. 지역 맛집·육아·중고시세의 본산(로그인월이라 난도 높지만 필수).
- **arca.live(~51M)·인벤(~49M)** — instiz보다 상위. 우선 추가.
- **82cook·여성시대·오늘의유머** — 여성·생활 관점(없으면 뷰티·살림 후기가 남초 왜곡).
- 보조: 유튜브 자막/댓글, 네이버 지도 리뷰(맛집), 당근(시세).

**우선 추가 순위:** 네이버 카페 → arca.live → 인벤 → 82cook.

## 7. 결론

> **제안(댓글 포함 본문 기반 + 호스트 분산 + curl/Playwright 선택 + 캐싱)은 기존 글감 수집 구조를 대체할 올바른 방향이며, 지금까지 실측한 모든 문제(차단·할루시네이션·글로벌 유출·응답성)를 하나의 구조 변경으로 동시에 해결한다.** 세 관점 만장일치로 "더 낫다". 단, **지연 규율(top-N·병렬·데드라인)** 과 **커버리지 보강(네이버 카페·arca·인벤·82cook)** 이 성패를 가른다.

### 다음 단계

1. 공통 `SourceAdapter` 인터페이스 설계(search→rank→fetch→parse, 공유 retry/cache/timeout).
2. 사이트별 티어 구현(curl 티어 먼저: bobaedream/ppomppu/instiz/dcinside-m/tistory → CF 티어: fmkorea/clien/ruliweb/theqoo).
3. 2단계 파이프라인 + 글로벌 데드라인 + 스트리밍을 `baseSearch.ts`에 반영.
4. Redis 시맨틱 캐시 + Postgres 콘텐츠 캐시([01]) 결합.
5. 커버리지 공백(네이버 카페·arca·인벤·82cook) 순차 추가.
6. 수정 후 [00]의 벤치마크 재실행으로 before/after 검증.
